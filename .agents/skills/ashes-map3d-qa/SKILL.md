# Ashes Throne — MAP-3D QA
[УТВЕРЖДЕНО владельцем 28.11.2026: методика и повторно используемый стенд; реализация проверяется отдельно.]
Read PROJECT_STATUS, AI_WORKFLOW, AI_SKILLS, MAP_3D_PLAN, current work branch handoff, this skill and ashes-babylonjs / ashes-level-design. Do not rely on chat memory. This is a QA workflow, not a game rule.
## 1. Diagnose before changing
- Reuse proven GitHub Actions Ubuntu + Playwright Chromium/WebKit, local checked-in Babylon and GLB loader in preview/map-3d/, existing MAP-3D-04 controller and Recast 0.43.1. Reference successful art run 46122416988 and movement #603; old green evidence is not current acceptance.
- Run a blank-canvas WebGL2 preflight once per environment before attempting scene import. If it fails, classify ENVIRONMENT_BLOCKED, stop local flag/CDN retries, move to known-good authorized runner. Never weaken sandbox, browser security or change game engine to make CI pass.
- No CDN in this preview, no dynamic runtime network dependency. Verify local script responses, engine version and canvas context. Distinguish runner setup, input delivery, asset integrity, actual import/render, camera, nav and gameplay failures. No claims of physical iPhone from software rendering.
## 2. Input contract
Use exact bytes from Library or a licensed tracked/released binary artifact; validate SHA256 + byte count and GLB header, expected visible triangle count, coordinates RH Y-up meters, camera targets and views; keep source, ART, NAV, markers and collision proxies distinct. Keep attribution and license per asset. If rights unclear, private authorized runner only. Avoid base64 text transfers/chunking as a production delivery strategy; never fabricate a substitute or expose tokens. If no approved binary transfer path, report INPUT_BLOCKED, save receipt and proceed with independently useful control tests, not a false candidate pass. Source and candidate hashes must survive new chat.
## 3. Reusable art gate
Use tools/map3d-qa/runner.mjs with a per-map manifest and exact GLB file; same tests for every art revision. Run Chromium/WebKit at 844x390 and 844x320; add 932x430 for gameplay/device parity. Real Babylon import, hash, actual rendered frames, visible geometry, canvas pixel variance, camera views, touch/resize, errors, lifecycle/dispose and re-entry. Log transfer/readiness, frame distribution, mesh/material/texture counts. Screenshots from actual render required; inspect them; CI green alone does not accept art. Software frame timing is diagnostic, not mobile performance. Test one control to validate infrastructure, never equate control pass with candidate pass.
## 4. Separate movement gate
Use the accepted MAP-3D-04/06 controller, do not implement a second movement engine for tests. Match collision/NAV revision with candidate hash, rebuild Recast from dedicated walkable proxies and authored obstacle footprints, not decorative high-poly geometry. Assert endpoint tolerance, no partial paths or illegal snaps, actual tap/arrival, alternate branches, stairs, blocked tap, retarget, stop, camera and repeated re-entry. Verify route clearance against art and check player camera for occlusion. Preserve reward/receipt contracts. Existing pilot test proves the controller only; map-specific markers and navmesh required before candidate gameplay pass. Never make a new battle list to fill test routes.
## 5. Evidence and continuity
Record candidate hash, PR/head SHA, runner run ID, artifacts, tests passed/failed/skipped, screenshot review and remaining device checks. Separate environment, rendering, navigation, gameplay, actual device, owner approval. Do not require owner to relay CI colors; check available API; if still running, provide link and exact pending gate, do not claim finished. Only applicable checks; no full unrelated suite for art-only change. Save restart pointer in PROJECT_STATUS and work branch START_HERE, update after each significant gate. No production merge before required gates.
