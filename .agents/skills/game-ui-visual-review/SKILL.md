# Безбожная приёмка UI
Собственная адаптация [Dune GoH #320](https://github.com/mryandexxx-spec/Dgoh-game/pull/320), по мотивам [Impeccable critique/audit](https://github.com/pbakaus/impeccable/tree/main/skill/reference) и [Microsoft frontend-design-review](https://github.com/microsoft/skills/tree/main/.github/skills/frontend-design-review). Полные внешние инструменты не установлены этим файлом.

1. Сравнить принятый оригинал (если есть), мастер и настоящие браузерные кадры при одинаковых данных и размерах; 844×390,932×430,844×320, при необходимости 667×375 и portrait. Playwright уже используется в проекте. Снимать все значимые состояния, закрытые/открытые узлы, текущий выбор, отмену, длинные подписи и переходы; проверять видимость CTA, касание и реальную достижимость, а не только отсутствие page overflow.
2. Независимый взгляд новичка без знания ТЗ: что это, куда нажать, зачем, что изменится, как вернуться? Проверять художественную иерархию, глубину, материалы, свет, цельность, соответствие лору и читаемость. P0 — сломан поток/данные; P1 — непонятный путь/нечитаемость/промах относительно эталона; P2 — заметное художественное несовершенство; P3 — мелочь. Не хвалить за количество итераций и зелёный CI.
3. Для диагностики можно использовать tools/ui-art/compare.py (Pillow отдельно от runtime): только одинаковые размеры и состояние, не ресайзить ради диффа; сохранять исходники. Метрики пикселей не художественная оценка.
4. Блокировать приёмку при P0/P1, потерянном обязательном эталоне, неработающих элементах, выходе за безопасные зоны, placeholder art или нечитабельном CTA. После двух провалов менять композицию/способ производства, не подгонять пиксели бесконечно. Отдельно реальные браузеры, физический iPhone и решение владельца. Сохранить конкретный вердикт, evidence и следующий этап в GitHub.
