# Пепельный престол — регламент работы AI-разработчика

**Назначение:** дополнение к инструкциям проекта ChatGPT. Здесь описан процесс работы, а не игровые правила. При противоречиях игровые решения сверяются с последним утверждённым GDD, архитектура — с актуальным TDD, фактическая реализация — с `main`.

## 1. Начало работы

1. Прочитай `docs/PROJECT_STATUS.md`, последнюю утверждённую редакцию GDD и документы, которые относятся к задаче.
2. Проверь актуальный `main`, нужные файлы, историю последних PR; не доверяй устаревшему снимку статуса.
3. Определи уже работающие функции, зависимости и риски.
4. Сформулируй минимальную цель и критерии готовности.
5. Не переписывай проект или смежные системы ради локального изменения.
6. Обозначай временные числовые параметры и демонстрационный контент как [ПРЕДЛОЖЕНИЕ] или тестовые.

## 2. GitHub-процесс

Репозиторий: https://github.com/mryandexxx-spec/ashes-throne-prototype  
Опубликованная версия: https://mryandexxx-spec.github.io/ashes-throne-prototype/

1. Создай тематическую ветку от текущего `main`.
2. Меняй только необходимые файлы, проверяй версии перед записью.
3. Добавь тесты; при исправлении ошибки — регрессионный сценарий, повторяющий её.
4. Запусти доступные проверки, честно зафиксируй, что именно выполнялось.
5. Создай PR с описанием изменений, изменённых файлов, тестов, рисков и ограничений.
6. **Не сливай в `main` без явного разрешения владельца.** Ответ «да» на конкретный вопрос о слиянии считается разрешением.
7. Перед merge проверь состояние PR и ожидаемый head SHA.
8. После merge сообщи PR и коммит. Не утверждай, что GitHub Pages уже обновился, пока это не проверено.
9. Дай короткий чек-лист для iPhone Safari, если менялись игра или интерфейс.

## 3. Обязательные проверки

**Логика:** инициатива и очередь, доступность действий, выбор живой цели, урон/эффекты, смерть, победа и поражение, повторный запуск, отдельные критичные крайние случаи.

**UI:** проверь реальные обработчики кнопок (не только внутренние функции), состояние disabled, переключение экранов, обработчики после сброса, отсутствие обращений к старой структуре состояния.

**Babylon.js:** сохранение жизненного цикла Engine/Scene, остановка render loop вне боя, отсутствие лишних созданий ресурсов или обработчиков, обновление mesh после изменений игрового состояния.

**iPhone:** landscape, portrait-подсказка, читаемость, управление пальцем, прокрутка, safe-area, видимость футера, отсутствие горизонтального переполнения, возврат из фонового режима Safari.

Автоматические модельные тесты **не заменяют** реальное устройство. Не называй код «проверенным на Safari» без мобильной приёмки. Если тест не запускался — укажи это прямо.

## 4. Ошибки и инциденты

При сообщении пользователя об ошибке:
1. Зафиксируй фактический симптом и где он проявляется.
2. Сопоставь симптом с последним изменением и актуальным кодом.
3. Воспроизведи в доступной тестовой среде, если возможно.
4. Исправь причину минимальным изменением в отдельной ветке.
5. Добавь регрессионный тест на пользовательский сценарий.
6. После разрешения слей PR и запроси повторную мобильную проверку.

Не переходи к новому большому этапу, пока в `main` остаётся известный блокер основного игрового цикла.

## 5. Документы и статусы

- **GDD:** согласованные игровые решения; не дублировать сюда.
- **TDD:** архитектура и технические ограничения.
- **Combat Specification:** конкретизация боевых правил.
- **PROJECT_STATUS:** короткий актуальный снимок завершённых этапов, блокеров и следующего шага.
- **Roadmap:** планы и приоритеты.
- **Changelog / PR:** история реализованных изменений.

Использовать статусы:
- [УТВЕРЖДЕНО] — согласовано владельцем.
- [ПРЕДЛОЖЕНИЕ] — ещё не утверждено.
- [В РАЗРАБОТКЕ] — работа или приёмка ещё не завершена.
- [РЕАЛИЗОВАНО] — создано и подтверждено соответствующими проверками; уровень проверки пояснить.

Обновляй `PROJECT_STATUS.md` после принятого этапа или при серьёзном блокере. Не используй его вместо полного Changelog. Не переписывай старые документы без необходимости; если GDD устарел, предложи точечную актуализацию.

## 6. Передача контекста между чатами

При росте контекста заранее предложи новый чат и подготовь компактный промпт:
- наименование проекта и направление работы;
- ссылки на `main`, `docs/PROJECT_STATUS.md`, актуальные GDD/TDD;
- последняя проверенная версия и результаты приёмки;
- незакрытые PR, блокеры и явно согласованные решения, ещё не попавшие в документацию;
- следующая задача и требование проверить факты по GitHub.

Новый чат должен читать документы, а не полагаться на то, что вся прежняя переписка доступна.

## 7. Взаимодействие с владельцем

Владелец проекта не обязан писать код. Если доступные инструменты позволяют, выполняй работу сам. Если запрошено задание для другого AI — предоставь готовый промпт: контекст, цель, действия, ограничения, мобильные требования, критерии приёмки, тесты, перечень изменённых файлов.

Предлагай решения с рисками, не соглашайся автоматически и не вводи неутверждённые механики. Одного ключевого вопроса обычно достаточно. Не говори о выполненной работе, если есть только план. Работай короткими проверяемыми этапами.

**Принцип:** изучить → согласовать → реализовать → протестировать → PR → разрешение на merge → мобильная приёмка → обновить статус.
