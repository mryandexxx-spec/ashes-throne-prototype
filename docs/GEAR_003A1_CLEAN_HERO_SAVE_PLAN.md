# Gear-003A1 — подготовка чистого сохранения героев, без подключения к игре

**2026-11-07 · [В РАЗРАБОТКЕ] · изолированный кодовый PR.** Разрешён только A1. **PR не сливать без отдельного согласия владельца.**

## Задача и решение владельца

В Gear-003F пользователь одобрил тестовые G1-бонусы по типам слотов, минимальные остатки материалов, а затем **предложил полностью обнулить всех старых героев** и пересоздать их без экипировки и ранее оплаченных уровней/G. Это противоречит варианту legacy, выбранному в той же анкете, поэтому позднее авторское условие трактуется как новое направление: **герои чистые, аккаунт и кампания без автоматического сброса**. Решение зафиксировано в `game-design/progression/DECISIONS.md` приватного архива (пункты 38–41, открытый PR #10).

**Область чистого старта:** уровень каждого из 5 тестовых героев = 1, G1 0/6, никакой экипировки или старых G-бонусов. Тестовые `classId` назначаются по Gear-003E. **Не обнуляются без отдельного разрешения:** Account XP, основная валюта, энергия, награды первого прохождения, сохранение кампании `ashes-throne.campaign.v1`, сохранение состава `ashes-throne.squad.v1`. Исторический запас C остаётся учтён в `legacyC` (не обменён, не потрачен). Компенсация ранее потраченной валюты не назначена. Старый исходный ключ хранится как резервный снимок; это не действующее legacy-оснащение.

## Изменения A1

- Новый `progress-v3-core.js` создаёт, проверяет и *только по прямому вызову* сохраняет v3 в отдельный ключ `ashes-throne.progress.v3`.
- Точка входа `fromV2`: использует старый `SaveCore.validate` для проверки и нормализации существующего v2, переносит только общие аккаунтные поля, создаёт каждого героя заново, включая пустую историю установок G1.
- `fresh`: создаёт совершенно новый v3 без старого профиля.
- `stage`: не переписывает `ashes-throne.progress.v2`, строго проверяет прочитанный и записанный v3, блокирует повреждённые сохранения; повторный вызов **не обнуляет** уже записанный v3.
- **Нет подключения к `index.html`, `game.js` и текущему `SaveCore.load`**. Новый модуль не загружается в опубликованном клиенте и никого автоматически не сбрасывает. Это осознанный предел A1: код контракта/тесты, не активная миграция.
- Новый тест `tests/gear-003a1-clean-migration.test.js` проверяет существующие G3, частичные G1, старые числовые слоты, сохранение аккаунта и C, ошибки JSON/хранилища, двойное выполнение, отсутствие подключения к UI.

## Ограничения A1

1. Объект v3 намеренно требует пустую экипировку G1 (это **контракт начального состояния**, не полнофункциональная модель будущих покупок). В A2 необходимо расширить валидацию под `itemId` и историю G-ступеней, после чего подключать к интерфейсу.
2. Техническая операция `stage` не обеспечивает межвкладочных транзакций. При будущей активации понадобится защита от конкурирующих записей и ошибок `localStorage` с понятным UI.
3. Подтверждение владельцем **масштаба фактического сброса** полезно перед merge/активацией A2; в этом PR старые пользовательские профили не затрагиваются.
4. Тестовые бонусы G1 и выдача новых материалов по Gear-003F будут частью A2, **не A1**.
5. Версия видимой игры `v0.3.42` не меняется, потому что новый модуль ещё не загружается страницей и не изменяет опубликованное поведение. При интеграции в клиент версию и футер обновить по `docs/AI_WORKFLOW.md`.
