# LC-006 · Сюжетные мостики к обязательным боям (технический адаптер)

**14 ноября 2026 · [В РАЗРАБОТКЕ: Draft PR, не `main`]**  
**Зависимость:** Draft #322 → Draft #323 → этот PR. Приватная литературно-игровая проба — отдельный Draft PR поверх private #64.

## Зачем

В обязательных боевых миссиях ранней версии FS-01 и FS-02 пользователь получал общую кнопку и новый 3D-бой без видимого мотива противников, а после победы — техническое «Следующий узел открыт». Это соединяло две механики, но **не связывало бой с событиями истории**. Владелец требует, чтобы бои были частью приключения.

Решение — контентно-нейтральный интерфейс для короткой постановки **до** сражения и отличающегося результата победы/поражения **после** него. Приватный сценарий включает собственные реплики, мотивы и последствия. Публичные файлы игры содержат **только формат, UI и проверки**, но не новые художественные сведения.

## Структура

К существующему `requiredBattleId` можно **опционально** приложить `requiredBattleNarrative`:

```js
{
  title: "Отдельное название боевого эпизода",
  intro: "Наблюдаемая ситуация и причина столкновения",
  lines: [
    { speakerId: "Рен Терен", text: "Короткая реплика" },
    { speakerId: "Нада", text: "Ответ" }
  ],
  victory: "Что происходит после записанной победы",
  defeat: "Что остаётся незавершённым после поражения"
}
```

Это **только данные**: никакого JS из текста, новых боевых формул, выпадения наград, изменения AI или повторных лорных выборов. Валидатор проверяет длины, типы, структуру и то, что это свойство принадлежит узлу с реальным обязательным боем. UI экранирует текст, для знакомых говорящих использует **существующие портреты**. Новые незнакомые NPC не получают выдуманных лиц.

Перед боем `LoreCampaignUI.renderResult` показывает сценический пролог в компактном полноэкранном режиме landscape (844×390/932×430), где текст при необходимости прокручивается только внутри панели, а кнопка «Вступить в обязательный бой» остаётся на месте. `game.js` переносит разрешённый объект в текущую попытку, показывает название боя на 3D-арене, а победу/поражение выводит через `textContent` вместе с сохранённым результатом. Если данных нет, сохраняется прежний безопасный технический UI.

**Критично:** `recordBattleVictory` и отдельный lore save по-прежнему решают, открывать ли следующий узел; авторский текст «победа» не является доказательством прохождения и не должен обходить сохранение.

## Канон, сохранения, риски

- В публичном `LoreCampaignData.catalog()` поля `requiredBattleNarrative` **нет ни у одного узла**; сцены всё ещё пусты до авторской приёмки. Приватный сценарий и неутверждённые события не скопированы в публичный GitHub.
- Отдельный закрытый проект использует гипотезу о **соперничающих проводниках, которые хотят первыми объявить об открытии**, а не внезапных «охранниках древней тайны». В этом документе **не утверждается**, что такая группа существует в каноне.
- Литературная глава не переписана и по-прежнему не содержит боёв.
- В полном тестовом билде боевой состав пока выбирается из всего игрового ростера; **не следует называть такой состав канонической экспедицией Рена и Нады**. Нужны отдельный авторский выбор и последующая доработка для точного 2-персонажного состава либо новая независимая игровая группа.
- Движок пока заканчивает сражение стандартной победой над противниками. Сюжетная цель «сберечь документ» **не имеет ещё отдельного тактического условия**; это будущее улучшение, не внедрённая механика. Аналогично универсальная арена не доказывает конкретную географию.
- Грубое столкновение не обязательно означает смерть: но боевые анимации сейчас могут выглядеть как смерть; потребуется визуальная приёмка и решение о нейтрализации.
- Новый формат не изменяет схему `ashes-throne.lore-campaign.v1` и не добавляет поля в `progress.v3`.
