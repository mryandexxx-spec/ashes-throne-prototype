## Общий принцип исполнения

Каждый этап имеет **цель → ограниченные файлы → тесты → критерий выхода → риск → отдельный PR → разрешение владельца на merge**. Следующий этап нельзя начинать на основе неслитого предшественника без явного основания и указания зависимости; нельзя выдавать локально написанный код за опубликованный. Весь документ — проектный план, а не подтверждение готовых функций.

| Этап | Зависимость | Результат | Что НЕ входит |
|---|---|---|---|
| **LC-000 / выбор дизайна** | текущие источники | Утверждённый формат адаптации, граница канона, типы узлов, первый срез | Код, экономические награды |
| **LC-001 / данные и проверка графа** | LC-000 | Чистые `LoreCampaignData` и валидатор структуры с тестовыми узлами; будущие флаги повторов/симуляции/мгновенной выдачи | UI, сохранение кошелька, новые бои |
| **LC-002 / карта и навигация** | LC-001 | Из существующего «Кампании лора» открываются история, схема карты, карточка узла, закрытый/открытый статус | Диалоги, баланс, GLB |
| **LC-003 / история, развилки и прогресс** | LC-002 | Универсальный исполнитель сцен/заданий, сохранение, повтор без изменения первоначального выбора, журнал ключевых решений | Награды, крупные линейки контента |

| **LC-005 / дополнительные типы задач** | LC-004 | Переиспользуемые задания наблюдения/сопоставления/выбора и необязательные ветви; без новых RPG-статов | Новые боевые формулы |

| **LC-009 / релизная полировка** | целостность предыдущих этапов | Полевые проверки, производительность, доступность, сохранения, регрессия, обновление статуса | Несогласованная инфраструктура |

**Порядок может измениться только через документированное решение**, например LC-006 можно отложить после LC-007, если владелец не разрешит неканонические боевые испытания. Отсутствие боевого контента в каноне **не является причиной выдумывать боевые сцены**. Наградные поля должны быть предусмотрены уже в LC-001, но реальные начисления — только LC-008.

## LC-000. Предпроектные решения и аудит

- Мир: `WORLD_STATUS.md` → `regions/gardens-over-abyss/CURRENT.md` → утверждённые части 1–13 → речевые паспорта → `AGENTS.md`; не заменять их старыми handoff и рабочими моделями.
- На момент составления дорожной карты игровой `main` `17fd802`, мировой `main` `858b195`. **Повторно сверять до любого PR.**

**Авторские вопросы (решить одним пакетом, без бесконечных уточнений):**
1. Лорная ветка — реконструкция уже написанных событий или отдельное приключение? **Рекомендация:** интерактивная хроника без реткона.
2. Достаточно ли первых трёх узлов для пользовательского пилота? **Рекомендация:** да, но показать содержательное действие и завершённую мини-арку.
3. Допускается ли размещать возле лорной истории **условные тренировочные** бои, не называя их литературным каноном? **Не добавлять до решения.**
4. Конкретные награды и стоимость — явно отложены, решение сейчас не требуется.

**Критерий выхода:** согласован объект разработки и границы допустимого сценарного изменения, история не переписана. Документы-предложения сами по себе не утверждают этот пункт.

## LC-001. Модель данных — первый технический PR

**Файлы-кандидаты:** новый `lore-campaign-data.js`, `lore-campaign-core.js`, `tests/lore-campaign-graph.test.js`; точный список согласовать с текущим деревом. Не править `CampaignCore` ради фиктивных миссий.

**Реализовать:**
- стабильные ID историй/глав/узлов, связи, координаты визуальных маркеров, признак обязательности;
- чистый `catalogIsValid()` (дубли, висячие ссылки, циклы обязательного графа, недостижимый конец, несуществующий тип и reward policy);
- вычисление доступности на основе основного прогресса;
- поля `replay`, `simulation`, `instantClaim`, `rewardPoolId:null`, `energyCostId:null`;
- явный результат `REWARDS_NOT_CONFIGURED` при попытке начисления, **без изменения кошелька**;
- тесты несанкционированного старта, невалидного узла, различия главной и необязательной ветви.

**Выход:** Node-тестами подтверждена целостная модель из нескольких тестовых узлов. Ни новая история, ни экономика не опубликованы.

**Риск:** несовместимые ID с будущими настоящими миссиями. Лечится пространством имён `storyId:nodeId` и запретом повторного использования.

## LC-002. Карта Садов — UI PR

**Файлы-кандидаты:** `index.html`, `styles.css`, небольшой экранный модуль `lore-campaign-ui.js` или локальные функции `game.js`, UI-тесты, `package.json` и футер версии.

**Реализовать:**
- точка входа на уже существующей карте хаба — `#campaignLoreContent`, НЕ новый пункт в основном меню;
- 2D фоновая схема без Babylon.js; 3 слоя «Город / Путь / Пять теней» — *географический смысл проверять приватно*;
- карточки доступных, закрытых и пройденных узлов, доступный текстовый список, видимая причина блокировки;
- компактная панель деталей без прокрутки всей горизонтальной страницы;
- фокус/aria, Escape, Back, удержание и возврат состояния выбора узла;
- скриншоты Chromium/WebKit 844×390 и 932×430, отсутствует горизонтальная прокрутка и перекрытие safe-area.

**Выход:** пользователь может попасть на карту и открыть/закрыть узел. Сюжетные действия пока не требуется симулировать.

**Риск:** художественная схема выглядит как ошибочная каноническая география. Маркировать «схематический маршрут»; не рисовать несуществующий прямой мост.

## LC-003. Исполнитель истории и безопасное сохранение

**Файлы-кандидаты:** новый `lore-story-runtime.js` (если оправдано), `lore-campaign-core.js`, UI-связка, тесты переходов и сохранений.

**Реализовать:**
- `beat` → действие/выбор → следующий `beat` → завершение узла; отсутствие динамического исполняемого кода из текста;
- `primary` vs `replay`, первый выбор фиксируется однажды; альтернативные ответы только в временном прогоне, без реткона;
- журнал ключевых решений первого прохождения, отдельный bestStars для рейтинговых узлов;
- независимый `ashes-throne.lore-campaign.v1` с валидатором, мягким добавлением новых узлов и устойчивостью к ошибке хранилища;
- checkpoint, отмена, возвращение с карты, новая сессия, «пропустить просмотренное» **без пропуска обязательных выборов**;
- клики не создают повторных событий, экран боя не грузится от просмотра диалога.

**Выход:** прогон тестового сюжета, перезагрузка страницы, повтор с альтернативой и неизменное главное решение.

**Риск:** повреждение всех локальных сохранений при ошибке в одной записи. Новый ключ хранить отдельно; старые `progress.v3` и `campaign.v1` не менять.

## LC-004. Пилот «Другая сторона»

**Контент:** FS-01 → FS-02 → FS-03, ориентир — первая принятая глава (редакция 1.3.1). Вершина — обнаружение несовпадения порядка имён в документах, **не разгадка всей истории**.

**Сценарий для пользователя:** зайти через хаб → выбрать историю → увидеть карту → открыть первую сцену → исследовать журнал и отдельный лист → выбрать порядок осмотра → получить подтверждение наблюдаемого различия → завершить часть → вернуться на карту → перезагрузить браузер → перепройти с другим порядком без изменения уже сохранённого первого.

**Перед кодом:** авторская редактура игровых сокращений и реплик; сверка Рена и Нады с речевыми паспортами. Не вставлять целиком главы в экран и не выдумывать угрозу боя.

**Выход:** один маленький, **законченный и понятный** пользовательский сюжетный цикл, в котором есть открытие, действие и результат. Показать владельцу для геймдизайнерского/художественного принятия.

**Риск:** скучное «нажми далее» вместо игры. Если у осмотра нет наблюдаемого результата и решения — возврат к геймдизайну, не расширять 15 узлов.

## LC-005. Задания и развилки

**Реализовать по потребности:** осмотр улики, сравнение сведений, выбор контакта/порядка, короткое событие с результатом, необязательные ветки и их соединение. Никаких отдельных шкал морали, расхода вымышленных предметов или RPG-статов.

**Выход:** три отличающиеся задачи проходят с понятными условиями, нет тупиков, необязательный путь не блокирует финал, повтор не меняет основной журнал.

## LC-006. Боевой адаптер и готовность повторных наград

**Не начинать пока не принят авторский статус условного боя.** Использовать действующий `CombatCore`, экран отряда и результат. Для обычного сюжета не создавать боевые противостояния.

**Заложить четыре отдельные операции:** ручной повтор миссии, существующий добровольный автобой, симуляция ×N, мгновенное получение ×1. Симуляция после заслуженных 3★, без входа в арену, с теми же согласованными затратами и повторными наградами, что ручная успешная попытка по утверждённой политике.

**Пока награды TBD:** соответствующие кнопки показывают объяснение, но не запускают выплату, не выдают нулевой «успех», не меняют энергию. В тестах запрет двойного начисления, обхода 3★, невалидного количества и отсутствующего сохранения. Изменение `progress.v3` запрещено без отдельной экономической спецификации.

## LC-008. Экономика и реальные выплаты — отложено

**Отдельный будущий выбор владельца:** повторные награды, первый проход, стоимость энергии, число повторов и дневные лимиты, бонусы 1–3★, допустимость симуляции для небойных испытаний. После утверждения — отдельные `RewardPolicy`/`Receipt`, безопасная миграция, повторно исполняемые транзакционные тесты. Не связать случайно сюжетный повтор с бесконечной добычей уникальных предметов.

## LC-009. Финальная приёмка

- Node: `npm test`, при сбое — точный отчёт и минимальное исправление.
- Браузер: Chromium/WebKit, карта → диалог → выбор → результат → карта; повтор, F5, отмена, offline/ошибка сохранения по мере доступности.
- Mobile emulation: минимум 844×390, 932×430, короткие landscape, portrait-подсказка, safe-area, 44px, клавиатура/ESC, no overflow.
- Прогресс: повтор не влияет на первичный выбор; симуляция не выдаёт «первую» награду и не работает до конфигурации.
- Регрессия: штаб, ростер, карточка, существующая учебная кампания, три миссии, бой, завершение, поражение, перезапуск, симуляция, награды и старый сюжетный sandbox.
- Фактический iPhone Safari (проводит владелец после опубликованного merge) — **первым пунктом сверить `vX.Y.Z · CODE` в футере**. До подтверждения опубликованного билда не заявлять приёмку.
- Содержательный обзор: текст не раскрывает прошлое из неверного источника, выборы живые, учебная карта не подменяет канон.

## Контрольные правила

1. Не выполнять LC-00N+1, если в LC-00N есть воспроизводимый P0/P1 блокер.
2. Каждый **кодовый** PR: версия в `package.json` + `#buildVersion`, автоматические проверки, описание изменённых файлов, оснований и рисков.
3. Отдельный сценарный PR не изменяет принятый художественный рассказ; статусы новых сцен — [ПРЕДЛОЖЕНИЕ] до принятия.
4. Нельзя считать слитым/опубликованным PR, пока реально не подтверждены состояние GitHub и публикация.
5. После **согласованного** этапа обновлять `docs/PROJECT_STATUS.md`, краткую историю в `docs/CHANGELOG.md` (если файл находится там; путь сверить) и эту дорожную карту; будущий чат начинает с файлов, не с воспоминания AI.
