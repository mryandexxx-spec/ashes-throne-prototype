## 1. Результат и рамки

В «Кампания» → «Кампании лора» игрок открывает обложку истории → схематическую карту региона → интерактивные узлы → диалоги/события/задания/условные боевые испытания → новые доступные узлы. Ветви могут расходиться и сходиться. После первого завершения можно **повторить узел, пересмотреть альтернативные ответы и улучшить оценку** без перезаписи основного сюжета. Реиграбельные наградные узлы имеют контракт будущих повторных наград, ручного повтора, симуляции и мгновенного получения результата. **Состав и числа наград, энергия и лимиты новых узлов остаются TBD**.

Система должна быть общей для будущих лорных историй; данные сценариев не должны находиться в гигантских обработчиках `game.js`.

Из утверждённого GDD 3.0: законченную миссию можно повторять, основной выбор при повторе не перезаписывается, альтернативные исходы — только просмотр; уникальная награда за первый проход не фармится; для боевых миссий оценка 1–3★, симуляция после 3★ в действующем прототипе; первое сюжетное завершение без затрат энергии, повторный фарм — за энергию/ресурс, параметры TBD. Сюжетные дополнительные ветви не должны блокировать основную линию.

## 2. Проверенный исходный код и необходимые адаптеры

Уже присутствует:
- `index.html`: `#campaignHub` с тремя направлениями: учебная, **«Кампании лора»** (пока заглушка «Пять теней»), основная «Путь к престолу»; `#campaignLoreContent` пуст, кроме текста; `#storyDemo` — **отдельная неканоническая проба**, не путать с новой системой.
- `game.js`: `showCampaignPath()` переключает направления, `renderCampaign()` рисует учебные миссии, `openCampaignMission()` запускает прежний бой, `simulateMission()` и `#simulationDialog` работают с существующей экономикой.
- `campaign-data.js`: главы, маршруты и зависимости `requiredMissionIds`; `campaign-core.js`: `completed` и `bestStars` по ID реальных `MissionData`.
- `mission-data.js`: три демонстрационные **боевые** миссии; `progress-core.js`: `MISSION_FARM`, `MISSION_GEAR_FARM`, `simulate`, `spendEnergy`, `claimFirstClear`; прогресс и кошелёк сохраняются отдельно.
- `story-demo-core.js`: ограниченный несохраняемый диалоговый сценарий. Архитектура пригодна как маленький образец чистых переходов, но его неканонический сюжет и состояние не использовать напрямую.
- `CombatCore`, `SaveCore`, `ProgressV3Core`, существующие экраны отряда/результата и Babylon.js — только через действующие интерфейсы.

**Не вставлять сюжетные узлы прямо в `MissionData`**: `CampaignCore` формирует ID из `MissionData.all()`, а экономика ожидает наградную боевую миссию. Это создаёт ложный бой для диалога и риск миграции сохранений. На первом этапе — отдельный **аддитивный, универсальный** модуль `LoreCampaignData` + `LoreCampaignCore`; интеграция с `CombatCore` через узкий адаптер. Не переписывать целиком учебную кампанию.

## 3. Сущности и формат сценарных данных

История (`story`): `id`, `title`, `subtitle`, `status`, `canonicalSource`, `chapters[]`, `mapLayers[]`, `entryNodeIds[]`.

Глава (`chapter`): `id`, `storyId`, `title`, `order`, `mapLayerId`. На экране — часть большой истории, а не обязательное новое географическое место.

Узел (`node`), стабильный ID с пространством имён (пример `five-shadows:fs-01`):
- `chapterId`, `title`, `mapLayerId`, `marker:{x,y}` в относительных координатах 0..1 (это **визуальная координата схемы**, не координаты мира);
- `kind`: `scene | investigation | task | choice | battle | finale`;
- `prerequisites`: массив существующих ID; `optional`: boolean; `nextNodeIds`: связи графа для отображения;
- `contentId` для отдельных реплик/целей и `canonicalRef` (часть/сцена; допускается приватная ссылка только в редакторском контуре);
- `firstClear`, `replay`, `rating`, `simulation`, `instantClaim` — **декларативная политика возможности**, не награда;
- `battleDefinitionId`: только у боевого узла и только после отдельного утверждения игрового контента;
- `rewardPoolId:null`, `energyCostId:null`, `dailyLimitId:null` пока экономика не утверждена. **Никаких фиктивных выпадающих предметов/валюты/XP**.
- `canonClass`: `source | adaptation | hypothetical`. Публичный текст маркирует игровые допущения, а приватный редакторский обзор хранит полную аргументацию.

Кадр диалога (`beat`): `id`, `speakerId`, `text`, `nextBeatId`, `choiceIds[]`, `onEnterEffects[]` только из строгого разрешённого набора (например, `markEvidenceSeen`), `skipSafe`. Не использовать исполняемые строки JS, `eval` или динамическое HTML из контента.

Вариант (`choice`): `id`, `label`, `nextBeatId`, `effects` из whitelist (локальное наблюдение, фиксируемый первичный выбор, открытие существующего пути). **Не разрешать условием внезапно убить персонажа, переписать канон или выдать предмет.**

Задача (`objective`): `id`, `kind` (`view | inspect | compare | choose | battleVictory`), `hint`, `required`. Для первой версии никаких квестовых таймеров, поиска скрытых пикселей или новой боевой системы.

Политика повторов/экономики отделена от нарратива (см. §7). Пример контракта — **схема, не действующая настройка**:

~~~json
{
  "id": "five-shadows:fs-02",
  "kind": "investigation",
  "chapterId": "fs-act-1",
  "prerequisites": ["five-shadows:fs-01"],
  "optional": false,
  "replay": {"allowed": true, "changesPrimaryStory": false},
  "rating": {"mode": "none"},
  "simulation": {"supported": false, "unlock": null},
  "instantClaim": {"supported": false},
  "rewardPoolId": null,
  "energyCostId": null
}
~~~

Для **боевого** узла при поздней настройке `rating.mode="stars-1-3"`, `simulation.supported=true`, `simulation.unlock="bestStars:3"`, `instantClaim.supported=true` — но **кнопки действуют лишь при настроенных правилах наград, стоимости, лимитов и успешном сохранении**. Повторять историю можно и без симуляции: это разные пользовательские действия.

## 4. Граф кампании и правила доступности

- Данные должны проходить проверку: уникальность ID, существование связей/глав, допустимые координаты, отсутствие циклов обязательного разблокирования, отсутствие несуществующих условий, достижимость финала.
- Основная линия последовательно открывает следующую точку. Дополнительные ветки могут стать доступными при достижении предшествующего основного узла; **их прохождение не требуется для основного финала**.
- Два варианта ответа могут временно вести на разные `beat`/узлы, но для первой версии сходятся обратно до следующего ключевого канонического события.
- **Прогресс завершения** и **оценка 1–3★** — отдельные счётчики. Чисто нарративный `scene` не получает боевую звезду за прокликивание; обоснованные правила оценки небоевых задач — отдельное авторское/геймдизайнерское решение.
- Блокировку узла проверять **и в UI, и в чистом ядре при запуске**. Нельзя стартовать узел через прямой вызов функции, подмену data-атрибутов или устаревшее состояние.
- Смена интерфейсной карты не меняет расположение героев в литературном мире; географические переходы/длительность описываются в сцене, не рассчитываются по нарисованной линии.

## 5. Состояние и сохранение

**Новый независимый ключ:** `ashes-throne.lore-campaign.v1`; старая `progress.v3` и `campaign.v1` остаются неизменными на пилотном этапе.

Пример полей:
- `version:1`;
- `stories[storyId].completedNodeIds[]`, `bestStarsByNodeId{}` (только рейтинговые узлы);
- `primaryChoicesById{}` — **фиксируются один раз** в основном прохождении;
- `keyDecisionLog[]` — только ключевые решения и существенные последствия;
- `seenBeatIds[]` / `seenEvidenceIds[]` — для пропуска просмотренного и продолжения;
- `activeNodeId` + `checkpointBeatId` — необязательная точка продолжения безопасного диалога;
- `schemaVersion` либо единое `version`, без противоречивых дублей.

**Основное прохождение** (`primary`): по завершении узла записывается выполнение, а первый выбор становится неизменным для последующей истории. **Повтор** (`replay`): запускается временная копия локального состояния, позволяет другие варианты и улучшение оценки (если предусмотрено), но не меняет `primaryChoices`, `keyDecisionLog` и ранее открывшиеся сюжетные пути. Только разрешённый результат оценки/фарм позднее может фиксироваться отдельно.

Сохранение: валидировать неизвестные ID и неверные типы, отклонять опасные части записи, не перетирать существующий профиль при повреждении нового ключа. При недоступном localStorage честно показать «Прогресс этого сюжета не сохраняется» и **не включать платное или мгновенное начисление**. Миграции сохранений версионировать, при создании будущих узлов восстанавливать отсутствие новых ID как не пройденные. Никакого реального аккаунта, сервера и защиты от читов сейчас нет.

## 6. Экран и UX (mobile-first)

**Навигация:** Штаб → Кампании → Кампании лора → «Пять теней» → карта → карточка узла → сюжетная сцена/задание/подготовка к бою → результат → карта. Возврат из прерванной сцены безопасен; после поворота/сворачивания сохраняется чекпойнт.

**Экран карты:**
- слева/в центре художественная **2D-схема** (SVG/изображение + HTML-маркеры), справа компактная панель выбранного узла; при нехватке высоты панель заменяется отдельным экраном подробностей без горизонтального скролла;
- главы и переключатель известных слоёв карты, ясные связи узлов; разные состояния: закрыто / доступно / пройдено / доступен повтор / оценку можно улучшить;
- открываемый маркер имеет минимум приблизительно 44×44 CSS px область касания, текстовый список узлов как доступная альтернатива карте и управление клавиатурой;
- статус прохождения, лучшая оценка и причина блокировки читаемы **без цвета**. Мини-карта не заменяет экран реплик.
- схема допускает художественное масштабирование, но не требуются Babylon.js, геодвижок, постоянный рендер и тяжёлый набор картографических библиотек.

**Карточка:** название, описание задачи, вид узла, условие открытия, статус, доступные действия: «Начать / Продолжить», «Перепройти», «Посмотреть историю», затем при наличии соответствующей политики «Симуляция», «Получить мгновенно». Пока экономика TBD, **не показывать ложные суммы, не проводить фиктивные начисления**; можно указать «Награды определим позднее», а экономические действия оставить disabled с объяснением.

**Сюжетная сцена:** крупный читабельный текст, имя говорящего, смена реплик и выбор; кнопка «Пропустить просмотренное» и корректный переход к ближайшему действию без пропуска обязательного выбора. Не отображать роман целиком в узком диалоге. Переходы и реплики — без дублированных слушателей при повторном входе.

**Визуальная система:** `docs/UI_DESIGN_SYSTEM.md`, `docs/UI_MIGRATION_PLAN.md`; графит, бронза, художественная сцена, одна иерархия HUD. Не возвращать legacy-синие полноразмерные блоки. Дизайн-контроль 844×390, 932×430, более короткие landscape, safe-area, portrait-подсказка, `prefers-reduced-motion`, фокус, Escape, без горизонтального переполнения.

## 7. Повторы, симуляция, мгновенное получение и будущие награды

Термины различать:
1. **Повтор сюжета** — просмотр и варианты без переписывания канонического выбора. Награда по умолчанию отсутствует.
2. **Ручной повтор наградного узла** — действительно пройти предусмотренное испытание заново, затем применить согласованный repeat reward.
3. **Автобой** — действующая арена, но алгоритм выбирает действия; это НЕ мгновенная симуляция.
4. **Симуляция ×N** — после достижения утверждённого условия (для боевого прототипа **3★**) пропускает бой и рассчитывает N разрешённых повторных наград в одной операции.
5. **«Получить мгновенно» ×1** — та же безопасная функция расчёта **одного** повторного результата без анимации и входа в бой; отдельная явная кнопка допустима, если UI её требует. Нельзя получать уникальную награду первого прохождения этим действием.

**Архитектурный порт [ПРЕДЛОЖЕНИЕ]:**
- `RewardPolicy.resolve(nodeId, mode, count, primaryProgress, wallet)` сначала возвращает описание допустимости / причины отказа, планируемые изменения и уникальный `receiptId`, **ничего не мутирует**.
- `RewardPolicy.commit(plan)` проверяет доступность сохраняемого кошелька, лимиты, энергию, повторные требования и идемпотентность; только затем фиксирует изменения.
- Пока `rewardPoolId=null`, возвращает `REWARDS_NOT_CONFIGURED`, не «успех с нулём награды». Кнопки получения недоступны. **Не добавлять тестовые ресурсы в производственный кошелёк.**
- В будущем одна транзакция должна охватывать списание энергии, начисление ресурсов, запись `receiptId` и увеличение счётчика попыток. Две отдельные записи localStorage НЕ атомарны; предпочтительно записывать кошелёк с квитанцией **одним** действием в текущую `progress.v3` (после согласованной миграции), а сведения о нарративном завершении сверять по квитанциям. При отсутствии безопасного механизма — не включать кнопку.
- Симуляции проверяют `count` как положительное безопасное целое, стоимость всего пакета и предел чисел до изменения состояния; двойной клик/повтор вызова с тем же `receiptId` не начисляет дважды.
- Первая победа не потребляет энергию в утверждённой кампанийной модели; повтор ради добычи потребляет ресурс, но стоимость/дневной лимит/награды этой лорной ветки — **TBD**.
- Не давать «бесплатную симуляцию» лишь потому, что ещё не утверждена экономическая стоимость. Нет экономических настроек — нет операции выплаты.

## 8. Интеграция с боем

- Не добавлять обязательный бой там, где он противоречит сюжету. Предложенный первый срез «Пяти теней» **небоевой**.
- Когда автор утвердит отдельные боевые испытания: адаптер вызывает существующий выбор отряда и `CombatCore`, возвращает итог в `LoreCampaignCore` по `nodeId`. Не вводить новых статусов или формул боя.
- При провале — не помечать узел пройденным; повторный вход и выход из боя надёжны.
- Для сюжетно обязательного персонажа, которого ещё нет в коллекции, предусмотреть отдельную временную сценарную команду, как в `StoryTrialData`, либо альтернативный путь — **не вербовать** его автоматически.
- Результат сражения не должен одновременно завершить `demo-mission-2`, отметить ежедневку учебной кампании или запустить неканоническую пробу.

## 9. Контракт ошибок, регрессии и производительности

**Чистые тесты:** валидация графа, нет циклических зависимостей, недостижимых финалов, несуществующих флагов; доступность; фиксация первого выбора; альтернативный просмотр; возобновление; неизвестные ID; безопасная миграция; невозможность незаслуженной симуляции; отсутствие экономических начислений при TBD.

**UI-тесты:** реальные клики на каждом этапе карты и сцены; назад во время диалога, после завершения, после проигрыша, из экрана отряда; повторный вход; обновление; фокус/клавиатура; touch markers; скрытые/disabled кнопки; отсутствие двойных событий.

**Регрессия игры:** обычная кампания и 3 демомиссии, звёзды, энергия, существующая симуляция, первая награда, ростер/карточка, снаряжение, бои, сохранения v3, старый сюжетный sandbox, хаб и штаб.

**Ресурсы:** 2D карта; тяжелые GLB загружаются только при действительном бою или на действующих экранах героев. Возврат на карту не оставляет лишний render loop. При многократных переходах количество обработчиков не растёт. Без новых npm runtime-зависимостей/сервера.
