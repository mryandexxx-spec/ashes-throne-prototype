# NET-002 — serial-выплаты разведсети, безопасное `progress.v3`

**Статус:** [В РАЗРАБОТКЕ], отдельная ветка `feat/net-002-network-rewards`, основана на ещё открытом NET-001 PR #386. Не подключено к `index.html`; никакой игровой баланс не утверждён и новые реальные награды не начисляются.

## Подтверждённая архитектурная основа

Текущая проверенная модель хранения — отдельный `network.v1` для результатов и общий кошелёк `progress.v3` для выплат. `ProgressWriterCore` управляет Web Lock, все изменения кошелька идут через эксклюзивную очередь. В NET-002 это правило сохраняется; нет второго кошелька, новых валют или серверной части.

## Изменения

- `ProgressV3Core.validateActive` принимает **необязательное** поле `networkLedger: {claimedThrough: uintSafeInt}`. Старые v3 без поля остаются допустимыми. Переход не требует сбрасывать профиль: новая запись появляется только при успешном `serial`-платеже. `toRuntime` / `fromRuntime` / обычный `persist` сохраняют поле без потерь.
- `RewardPolicyCore`: новый `kind: "serial"`. Платёж разрешён только для номера **ровно** `claimedThrough + 1`. Для повторного номера — `ALREADY_CLAIMED`; для пропущенного — `SERIAL_OUT_OF_ORDER`. Обычные `first-clear`, `repeat`, `best-stars` продолжают использовать прежние квитанции. `serial` не добавляет квитанции, не расходует энергию, не зависит от дневных лимитов. Запись ресурсов и счётчика в один `progress.v3` атомарна для одной записи.
- `heroShards` — **только для `serial`**; контроль известного ID героя, целочисленной суммы, безопасного переполнения, начисление через существующий `StarCore.add`. При 7★ выдача с осколками отклоняется: `SHARDS_AT_MAX_RANK_UNRESOLVED`. Нет самодельной компенсации — требуется решение владельца к NET-006.
- `network-reward-core.js` — изолированный адаптер. На каждом `claim` перечитывает именно **сохранённый** `network.v1`, требует `completed[].status="done"`, `kind="manual"`, правильный порядковый номер и `rewardRef`. Нет сохранённой победы — нет выплаты. Режим не подключён к `game.js`, в коде **нет production-наград**.
- `NetworkCore.compactCompleted` сохраняет обратную совместимость со старыми `network.v1` без поля `completedThrough`; на основании уже оплаченного `claimedThrough` можно удалить только оплаченные записи. Прерывание компактизации не отменяет выплаченные деньги и не удаляет неоплаченные операции.

## Конкуренция и отказы

При подключении к игре требуется `ProgressWriterCore.exclusive` и владение `ProgressWriterCore.isOwner`, как у LC-008F. После неясного `setItem` или неверного readback `NetworkRewardCore` блокирует сеанс до перезагрузки. Перезагрузка восстанавливает факт выплаты из durable `networkLedger`, исключая повтор.

Нет транзакции между двумя разными `localStorage` ключами: это сознательное ограничение. Сначала победа записывается в network, затем кошелёк получает разовую последовательную выплату. Компактизация выполняется отдельно и **не обязательна** для успешной выплаты. Старые непогашенные операции сохраняются при отказе в записи кошелька.

## Разграничение баланса и контента

Тесты используют только вымышленные технические `synthetic-*` источники и небольшие числа, которые **не являются** игровым балансом. В продакшене источник выплаты должен подбираться по проверенному справочнику `rewardRef`, утверждённому в NET-006. Прямой произвольный `source` в будущем UI не допускается: это вход в доверенный backend-adapter, а не пользовательский ввод.

Поле `heroShards` пока не задаёт компенсацию за осколки свыше 7★. Поздние материалы G9–G13 не вводятся, игровое состояние боя, экономика текущих миссий и пять разовых наград LC-008F не изменяются.

Полный `npm test` и браузерные workflows должны быть подтверждены на финальном head PR.
