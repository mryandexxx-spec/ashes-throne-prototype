# Пепельный престол — Technical Design Document (TDD) 1.0

**Дата:** 5 ноября 2026 г.  
**Статус:** [ПРЕДЛОЖЕНИЕ — технический проект для согласования], не описание уже реализованной архитектуры.  
**Источники:** GDD 3.0; `Project_work.md`; статический аудит архива `AshenThrone_BabylonStarter_MobileScrollFix.zip`.

## 1. Цель и ограничения

Развивать браузерную мобильную пошаговую RPG на существующей основе Babylon.js, не переписывая рабочий прототип ради абстрактной архитектуры. Главная платформа — смартфон в горизонтальной ориентации; PC-браузер дополнительный. Основной бой — ручной выбор способностей и целей; автобой — опционально. Этот TDD описывает **план развития**, а не заявляет о готовности запланированных систем.

## 2. Что существует сейчас [СТАТИЧЕСКИ ПОДТВЕРЖДЕНО]

- `index.html`: экраны главного меню, коллекции, заглушки кампании и боя; Babylon.js загружается по CDN.
- `styles.css`: оформление экранов, адаптация по ширине до 700px.
- `game.js`: данные пяти демонстрационных бойцов (3 союзника / 2 противника), навигация, минимальная логика боя и построение Babylon.js-арены.
- `README.md`: инструкция запуска и описание стартера.

Нет настоящих отдельных модулей, полноценного хода по скорости, способности как системы, прогрессии, данных миссий и сохранения.

## 3. Принципы развития [УТВЕРЖДЕНО В GDD]

1. Сохраняем Babylon.js и используем его для 3D-арены; интерфейс можно оставлять на HTML/CSS, если он подходит.
2. Изолируем игровые правила от отрисовки, чтобы бой и персонажи проверялись независимо от 3D.
3. Храним описания персонажей, способностей и миссий отдельно от механизмов их исполнения, когда сложность это оправдывает.
4. Каждая доработка локальна; не переписываем всю игру и не вводим сложный сборщик без практической необходимости.
5. Следим за памятью, CPU, GPU, графическими ресурсами и обработчиками/таймерами/циклами.
6. Не называем локальное сохранение защищённой серверной системой.

## 4. Целевая схема модулей [ПРЕДЛОЖЕНИЕ]

Схема логическая. **Она не означает требование сразу создавать отдельный файл для каждой строки.**

| Граница | Ответственность | Не должна делать |
|---|---|---|
| Application / Navigation | Смена экранов, запуск/завершение игровых сценариев | Вычислять урон, управлять внутренностями meshes |
| Game Data | Описания героев, способностей, миссий и наград | Напрямую менять DOM или Babylon.js Scene |
| Roster / Progress | Полученные герои, уровни, состав отряда | Управлять камерой и интерфейсом боя |
| Combat Rules | Очередь, действия, разрешение эффектов, победа/поражение | Вызывать HTML, создавать Babylon.js Mesh |
| Combat Presentation | HTML-панель, подсветка выбора, визуальные эффекты и 3D-арена | Самостоятельно рассчитывать игровые правила |
| Persistence | Сохранение/загрузка версии состояния | Содержать бизнес-правила и графику |

В ближайшей версии оставить существующую структуру и выделять эти границы **по мере добавления нового поведения**. Решение о реальном разбиении `game.js` — после стабилизации и отдельной проверки.

## 5. Потоки данных [ПРЕДЛОЖЕНИЕ]

**Нажатие игрока:** UI → запрос действия → правила боя проверяют допустимость → обновление боевого состояния → UI и Babylon.js показывают результат.  
**Ход противника:** правила боя → выбор допустимого действия по алгоритму → новое состояние → отображение.  
**Завершение миссии:** результат боя → правила наград → обновление прогресса → сохранение → интерфейс наград.

Источник истины — игровое состояние, а не текст кнопок, DOM-атрибуты или состояние 3D-мешей.

## 6. Технические решения для ближайших этапов

### 6.1. TECH-001 — стабилизация [ПРЕДЛОЖЕНИЕ]

Оставить четыре файла, исправить опасные обработчики/переходы и проверить загрузку Babylon.js/дополнительных материалов. Новый боевой движок пока не писать.

### 6.2. TECH-002 — мобильный интерфейс [ПРЕДЛОЖЕНИЕ]

Добавить подсказку при портретной ориентации, проверить маленькую высоту в landscape, управление касанием и скролл. Подсказка не должна менять сохранённое состояние игры и блокировать исходный код браузерным orientation lock.

### 6.3. TECH-003 — lifecycle [ПРЕДЛОЖЕНИЕ]

Определить единое владение `engine`, `scene` и созданными ресурсами. При уходе с арены минимизировать ненужный рендер. При окончательном уничтожении сцены освобождать Babylon.js ресурсы. Не добавлять много обработчиков `resize` и render loop при повторных входах. Проверять результаты измерениями.

### 6.4. TECH-004 — подготовка к бою по GDD [ПРЕДЛОЖЕНИЕ]

Только после исправления существующих проблем — выделять боевое состояние и проверки действий из графического слоя. Порядок ходов, формулы и способности фиксировать в отдельной Combat Specification до реализации спорных параметров.

## 7. Проектирование сохранения [ПРЕДЛОЖЕНИЕ, НЕ УТВЕРЖДЕНО]

Для вертикального среза рассмотреть версионированное локальное сохранение с явными полями `schemaVersion`, коллекция, уровни героев, состав отряда и завершённые миссии. Проверять пустые, устаревшие и испорченные записи, предусмотреть безопасный сброс тестового прогресса. Решение между `localStorage` и IndexedDB принять после оценки объёма данных. Не хранить там секреты или доверенные платежные данные. Защищённый онлайн-прогресс требует сервера в будущем.

## 8. Требования к проверке каждой задачи

- Функциональные: загрузка, переходы, действия, граничные ситуации, повторные запуски.
- Мобильные: landscape/portrait, короткий viewport, касания, прокрутка, отсутствие горизонтального переполнения.
- Ресурсы: память, CPU, GPU, Babylon.js Scene/Mesh/Material/Texture, обработчики/таймеры/render loop.
- Отчёт: что реально запускалось, где проверялось, какие файлы изменены, что не удалось измерить.

Конкретные целевые показатели FPS, памяти, размера загрузки и список поддерживаемых устройств **TBD**; не выдумывать численные пороги до технического тестирования.

## 9. Нерешённые вопросы (не принимать без согласования)

- Формула инициативы и ходов; перезарядки и статусы; действия врагов и автобоя.
- Способ хранения игровых данных и границы физических модулей.
- Локальное хранение и будущая серверная архитектура.
- Загрузка, кеширование и версии 3D-ресурсов.
- Устройства и браузеры для обязательной регрессии, целевые показатели производительности.

## 10. Критерий завершения технической базы

Исходный прототип запускается и проходит подтверждённые базовые тесты; проблемные переходы и перезапуски исправлены; мобильные ограничения описаны и проверены; для следующей задачи есть локальная архитектурная граница; изменения документируются. Пока часть проверок не выполнена, этап остаётся **[В РАЗРАБОТКЕ]**.
