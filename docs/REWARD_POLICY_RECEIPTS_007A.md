## 2. Правило транзакции

1. **Сначала завершение и подтверждение** в самостоятельном сейве режима, затем отдельный claim. Никакой записи кошелька в обработчике просмотра реплик и никакой двойной записи кошелёк+сюжет под видом одной атомарной транзакции.
2. **Перечитать актуальный v3**, проверить schema и revision, право на награду в уже сохранённом доменном состоянии и отсутствие того же receiptId.
3. В едином JSON объекта v3 записать изменение currency, accountXp, материалов, энергии, revision и rewardReceipts. До подтверждённой записи ничего не показывать как выданное.
4. При отказе записи оставить право на claim в самостоятельном сейве режима. При неясном результате записи вернуть SAVE_OUTCOME_UNKNOWN и заставить интегратор перечитать Receipt, не повторять награду с новым ID.
5. Если сейв режима отсутствует или повреждён, доказательство не проходит. Не восстанавливать достижения из UI, незаписанного runtime или неподтверждённого runId.

## 3. Реализовано в этом PR

- reward-policy-core.js — чистый resolve для превью и отдельный асинхронный claim; обязательные адаптеры authorize (подтверждённое сохранённое событие) и exclusive (общая эксклюзивная запись кошелька); без них отказ. **Файл не загружается в index.html, live-каталога нет**.
- Receipt имеет поля id, sourceId, day, count; его ID составлен из типа first-clear / best-stars / repeat, устойчивого sourceId и occurrenceId. Для пяти актов в будущей интеграции occurrenceId должен быть постоянным once, для оплачиваемого повторного запуска — настоящим стабильным runId. Получение по тому же ID дважды запрещено.
- progress-v3-core.js принимает *необязательный* массив rewardReceipts и переносит его при toRuntime, fromRuntime и persist. Старые v2/v3 без нового поля сохраняют прежние балансы. Неверные записи/дубли не нормализуются молча — профиль блокируется. Ёмкость журнала сейчас ограничена 10 000 записями: при достижении лимита fail-closed, никакого удаления старых IDs.
- tests/reward-policy-007a.test.js — исключительно синтетические количества наград для тестирования контракта. Примеры callback-авторизации не являются готовым адаптером к production lore/challenge/ops.

## 4. Граница гарантии и обязательный следующий этап

**Критический блокер:** даже один JSON с Receipt не даёт настоящего межвкладочного compare-and-swap. Сейчас другие способы записи v3 (обычная кампания, энергия, daily/login, экипировка) не используют общий serializing writer. Поэтому в реальном интеграторе нельзя просто передать любой callback как exclusive и считать проблему решённой. До первых live-наград требуется единый проверенный механизм эксклюзивности для **всех** авторов v3, либо транзакционное хранилище. На браузерах без механизма гарантия должна fail-closed. Сам по себе localStorage не защищает от ручной правки игроком.

Пока сохраняются существующие LoreCampaignCore.rewardCheck = REWARD_ENGINE_NOT_IMPLEMENTED / REWARDS_NOT_CONFIGURED; rewardPoolId, energyCostId и dailyLimitId остаются null. Без допущения, что сюжетный replay, проверка альтернативного выбора или осмотр даёт приз. Не приравнивать небойный узел к 3★. Первые сюжетные прохождения бесплатны.
