# Stats-001C — исследование обороны и Protection

**Дата:** 2026-11-08. **Статус: [УТВЕРЖДЕНО ДЛЯ ТЕСТОВОГО ПРОТОТИПА]** — владелец ответил «Ок» на прямой вопрос об утверждении модели A (K=100), порядка обработки урона и следующего opt-in этапа. **[В РАЗРАБОТКЕ]** — код кандидата `v0.3.51 · STATS001C` в PR #111, без слияния и без приёмки на iPhone. Это не утверждает финальных характеристик или баланса будущей RPG.

## 1. Исходные ограничения

**[УТВЕРЖДЕНО]** По `game-design/progression/DECISIONS.md` (worldbuilding/main, пункты 7–8):
- Protection — **отдельная шкала, поглощающая урон раньше HP**. Это не обычная процентная защита и не физическая/магическая оборона.
- Физическая и магическая оборона — разные характеристики.
- Обычное лечение восстанавливает **HP**, а Protection способны восстанавливать только специально предусмотренные умения.
- Protection не восстанавливается автоматически каждый ход.
- Числовые формулы и базовые показатели **не утверждены**.

**[РЕАЛИЗОВАНО]** В игре `v0.3.50 · STATS001B`: `damageType:"physical"|"magical"` только у тестовых способностей; без поля — `legacy` и общая `atk`. Текущая цепочка повреждения `dealDamage`: `rawDamage → weakening ×0.7 → guard ×0.5 → HP`, с `Math.round` на каждом из двух модификаторов. `guardHits` — статус, который тратится на попадания, **не запас Protection**. Реальные игроки/враги используют legacy, и существующие тесты проверяют старые суммы.

## 2. [ПРЕДЛОЖЕНИЕ] Модель обороны A — убывающая отдача (рекомендована для прототипа)

Для физического урона использовать `physicalDefense`, для магического — `magicDefense`. Для уже определённого после модификатора способности входящего урона `D`:

```text
D_after_defense = round(D * K / (K + DEF))
K = 100  // СТРОГО ТЕСТОВОЕ предложение, не утверждённый баланс
DEF >= 0
```

*Уточнения:* `round` означает положительное округление как `Math.round` в JS; DEF целая или неотрицательная конечная величина, окончательный формат значений TBD. Не использовать магическую оборону против физического удара и наоборот. Protection не участвует в формуле обороны. При `DEF = 0` урон не меняется. Пробивание обороны будет определено в отдельном этапе и сейчас не включается.

| DEF | Урон при D=40 | Погашено обороной |
| ---: | ---: | ---: |
| 0 | 40 | 0% |
| 25 | 32 | 20% |
| 50 | 27 | ~33% |
| 100 | 20 | 50% |
| 200 | 13 | ~67% |
| 400 | 8 | 80% |

**Сильные стороны:** неотрицательный урон; отсутствие жёсткой границы, где дальнейшая оборона бесполезна; действует одинаково для обеих школ; позволяет отдельно балансировать рост обороны и ATK. **Слабость:** `K=100` предполагает масштаб будущих показателей: пока нет согласованных значений героев/врагов, он не может считаться окончательным. При чрезмерных DEF бой затянется. Тестовые пороги следует валидировать против миссий #1–#3.

### Альтернативы

- **B. Линейное вычитание:** `max(0, D - DEF)`. Понятно игроку, но маленькие удары перестают наносить урон при высокой защите, а большой урон становится непропорционально выгодным. Для RPG с множеством малых и массовых ударов не рекомендовано.
- **C. Линейный процент с пределом:** `round(D * (1 - min(DEF / 200, 0.75)))`. Простой прогноз, но резкий потолок 75% обесценивает рост после DEF=150. Может потребовать специальных исключений для будущего пробивания. Не рекомендовано на этом этапе.

## 3. [ПРЕДЛОЖЕНИЕ] Порядок полного удара

**Рекомендованная цепочка для физического/магического типа:**

1. Выбрать только явно заданную `physicalAttack` или `magicAttack`; множитель способности округлить один раз (как сейчас).
2. Применить текущее ослабление атакующего (`×0.7`, `Math.round`), если активно.
3. Применить соответствующую DEF по модели A (в отдельном шаге с округлением).
4. Применить текущий guard (`×0.5`, `Math.round`), потратить ровно одну `guardHits` на получателя.
5. Списать остаток **с Protection**, в размере `min(incoming, currentProtection)`.
6. Остаток списать с HP, не ниже нуля. Урон выше доступного HP не создаёт отрицательных значений.
7. Обновить поля результата и события для UI/лога. Победа/поражение определяются по HP, а не по Protection.

**Пример:** магическая атака с `rawDamage=40`, дебаффом атакующего, `magicDefense=50`, действующим guard и Protection=6:

```text
40 → weakening 28 → магическая оборона 19 → guard 10
Protection: 6 → 0; HP: 100 → 96 (потеря 4)
guardHits: 2 → 1
```

Для `legacy`-ударов **оставить прежнюю цепочку без DEF/Protection**, до отдельного перехода существующих героев/способностей. Это осознанное временное ограничение ради отсутствия регрессий, а не правило конечной игры.

**Особые случаи для реализации:** Protection=0; Protection больше полученного урона; 0 урона; групповая атака с разной обороной/Protection у целей; два типа урона в разных умениях; смертельный удар; бой с волнами; автоатаки врагов; исцеление HP при активной Protection; повреждение из статусов (не смешивать с прямой атакой без отдельного правила).

## 4. [ПРЕДЛОЖЕНИЕ] Состояние и события

- На боевом бойце хранить `protection` (текущий запас) и `maxProtection` (максимальный запас); при инициализации проверять согласованность `0 <= protection <= maxProtection`.
- **Не добавлять Protection всем реальным персонажам с нулём по умолчанию как будто это утверждённый стат.** Нулевые значения допустимы только в явно сконструированных тестовых фикстурах; фактическая величина в составе кампании требует авторского решения.
- Для явно типизированного `damage`-события предложить дополнительные поля: `damageType`, `protectionDamage`, `hpDamage`, `remainingProtection`, `remainingHp`. Отдельно решить, означает ли прежнее `amount` итоговый урон до распределения между Protection/HP или фактическое уменьшение суммарного ресурса; **не менять значение `amount` у legacy**.
- Контрольные поля при загрузке `progress.v3` не меняются: Protection — боевое состояние, не новая валюта и не сохраняемый вне боя остаток.
- Обычное `heal` не затрагивает Protection. Будущая отдельная способность `restoreProtection` требует явного типа, ограничения максимумом и события. Не добавлять автоматическое восстановление на ход/волну.
- Информация о двух шкалах должна показываться на HUD до включения Protection у реальных бойцов; не создавать нечитаемые подписи на маленьком iPhone.

## 5. Проверки перед внедрением

- Тестировать физическую и магическую оборону отдельно: при `DEF=0` исходный типизированный урон сохранён; `DEF=25,50,100,200` соответствуют таблице; противоположная DEF не действует.
- Регрессия: все предыдущие `64/64` теста, особенно ослабление → guard → HP, одиночные/массовые способности, поведение врагов, бой с волнами и сохранения — без изменений для legacy.
- Для Protection: меньше входящего урона, ровно столько же и больше, отсутствие регенерации, guard уменьшается на одну единицу за удар, healing восстанавливает только HP, смерть только при нуле HP.
- Исключить `NaN`, отрицательные и бесконечные значения из новых числовых полей; не допускать частично применённой команды при неверных характеристиках.
- До включения в реальные миссии выполнить контролируемый балансовый прогон: 0 / лёгкая / тяжёлая оборона, короткие и длинные схватки, ручное и автоуправление, обе школы урона.
- После игровой реализации: первый пункт мобильной проверки — сверить новую метку сборки, затем проверить iPhone Safari landscape, HUD Protection, выбор цели, группы, победу/поражение, повтор, возврат из фонового режима, сохранение.

## 6. Подтверждение владельца и границы реализации

1. Подходит ли модель A (убывающая отдача), с **тестовым** K=100, для начального прототипа?
2. Верен ли предложенный порядок `weakening → DEF → guard → Protection → HP`?
3. Разрешить ли реализацию в виде строго **opt-in тестовых персонажей/боёв** без перераспределения характеристик и способностей существующих героев? Для реальной кампании позже понадобятся базовые числовые значения и перенос навыков из legacy.

**[УТВЕРЖДЕНО ДЛЯ ПРОТОТИПА — 08.11.2026]:** модель A, K=100, цепочка `weakening → DEF → guard → Protection → HP`, первичная реализация только для явных типизированных атак тестовых бойцов. Механика защищена от применения к прежним `legacy` атакам.

**[РЕАЛИЗОВАНО В ВЕТКЕ — до слияния]** `combat-core.js` применяет DEF по типу и отдельную `protection/maxProtection`-шкалу **только при наличии явно типизированной атаки**; отсутствие полей DEF или Protection означает, что эти механики для цели пока не активированы, а не действительные базовые значения характеристики. Отрицательные/нечисловые значения и неполный запас Protection отклоняют типизированное действие до расхода хода. Для групп проверяются все цели до первого повреждения. Поля урона в событиях дополняются `protectionDamage`, `hpDamage`, `remainingProtection` (null, если запас не определён), а `amount` остаётся рассчитанным входящим уроном после ослабления/DEF/guard, до распределения по двум шкалам. У `legacy`-событий формат остаётся прежним. `tests/stats-001c-defense-protection.test.js` содержит проверочные векторы.

**[НЕ УТВЕРЖДЕНО]** финальные числовые характеристики героев, значения DEF, величина/источники Protection для сюжетных персонажей, баланс формул за пределами тестового прототипа, новое UI двух шкал для реального боя и типы действующих навыков. В тестовой ветке не создаются ни реальные защищённые герои, ни новые действующие игровые способности.

**[НЕИЗМЕННО]** старые вычисления ослабления, guard и HP, награды, энергия, прогресс v3, инициатива, автоигра. Обычное лечение не влияет на Protection, автоматической регенерации нет.

**[КРИТЕРИЙ ПРИЁМКИ]** после успешного CI и отдельного разрешения владельца на слияние — в iPhone Safari сначала сверить футер `v0.3.51 · STATS001C`, затем обычный бой, навыки, победу/поражение, повтор боя, восстановление сессии. UI двух шкал не показывается в сюжетных миссиях, пока их характеристики не назначены.
