# UI-MIGRATION-001 — план перевода игры на единый интерфейс

**Статус:** [В РАЗРАБОТКЕ] инвентаризация текущего `main` на 10.11.2026; порядок этапов — [ПРЕДЛОЖЕНИЕ] до отдельного согласования и PR по каждой группе. **[УТВЕРЖДЕНО]** направление: язык HQ-UI-008 + ROSTER-UI-006 обязателен для существующих и будущих экранов.

## 1. Подтверждённый объём

В `index.html` обнаружено **17 разделов `.screen`**, **5 HTML `dialog`**. Штаб `#home` и коллекция `#collection` — принятые стилевые ориентиры, остальные требуют аудита/визуальной приёмки по отдельности. Наличие экранов в DOM **не доказывает**, что каждый из них работает без ошибок на реальном iPhone.

| Экран / модуль | Текущее состояние | Требуемый план |
|---|---|---|
| `home` | Принятая сцена штаба | **Эталон:** сохранить расположение интерактивных предметов, художественный фон и HUD |
| `collection` | Принятый ROSTER006 | **Эталон:** база scene shell + архивная панель + карточки |
| `heroDetail` | Отдельное досье | Приоритет 1: перенести контекст HUD, панель, теги, прогрессию и портрет с сохранением фокуса на герое |
| `squad` | Экран выбора команды | Приоритет 1: художественный выбор отряда, сохранять 1–5 героев, лидера и старт боя |
| `playerProfile` | Самостоятельный экран профиля | Приоритет 2: единый HUD и карточки сведений, без изменения аккаунта/локального сохранения |
| `dailyTasks` | Ежедневные задания | Приоритет 2: список задач, статусы, награды, disabled/claimed |
| `loginCalendar` | Календарь входов | Приоритет 2: календарная сетка и награды в общем стиле, проверка маленького landscape |
| `campaign` | Список глав/миссий | Приоритет 3: единая сцена и ясная иерархия глав, миссий и статусов |
| `challenges` | Испытания | Приоритет 3: условия доступа, два режима, подготовка и результаты |
| `operations`, `signalOperations` | Два сценария разведопераций | Приоритет 3: единая визуальная система для маршрутных карт и инструкций, не менять бизнес-логику |
| `operationResult`, `signalOperationResult` | Результаты операций | Приоритет 3: общий компонент результата, разные данные и действия |
| `missionResult`, `challengeResult` | Результаты боя и испытания | Приоритет 3: общий результат, избегать копирования конфликтующих стилей |
| `storyDemo` | Изолированная сюжетная проба | Приоритет 4: литературная читабельность, диалоги, выборы, отсутствие зацикливания |
| `battle` | Полноэкранная Babylon-арена | **Отдельный HUD-проект:** только стилистическая интеграция, не накрывать арену архивной панелью, не менять боевые правила и lifecycle |

Пять диалогов из `index.html`: `skillUpgradeDialog`, `gearPromotionDialog`, `simulationDialog`, `heroBiographyDialog`, `lockedHeroDialog`. Все входят в работу над общими диалоговыми паттернами, но могут мигрировать вместе со своими экранами.

## 2. Предлагаемые этапы

### UI-FOUNDATION-001 — единые визуальные контракты

- Закрепить `docs/UI_DESIGN_SYSTEM.md` и список экранов в регламенте.
- На основе принятого ростера отобрать повторяемые значения (не переносить все 100+ селекторов как есть).
- Подготовить небольшие *неразрушающие* классы: `ui-scene`, `ui-hud`, `ui-panel`, `ui-section-heading`, `ui-button` (имена условные).
- Пилотный экран: досье героя. Без глобального переписывания `.screen`, `.hero-card`, `.battle-*`.

### UI-HERO-001 — досье и управление отрядом

- Досье и экран отряда: оформление с сохранением всех данных, эволюции/экипировки, `★ Лидер` и тегов персонажа.
- Сохранять работающие обработчики, прокрутку между коллекцией и досье, повторное возвращение.
- Приёмка на iPhone — отдельный шаг после CI и разрешения на merge.

### UI-SYSTEMS-001 — профиль, задания и календарь

- Одна художественная логика панелей, метрик, списков и календаря.
- Проверить получение наград и блокировку повторной выдачи; не менять алгоритмы начисления.

### UI-MODES-001 — кампания, испытания, операции и результаты

- Ввести единые стили заголовков, выборов, таблиц/маршрутов, наград и результатов.
- Удержать различия между сюжетной миссией, испытанием и разведоперацией.

### UI-STORY-001 — история и биографии

- Типографика, чтение и диалоги; акцент на содержании, а не бронзовых рамках.
- Особое внимание короткой высоте landscape и системной клавиатуре/диалогам.

### UI-COMBAT-HUD-001 — визуальное соответствие боевого UI

- Перевод существующих HUD, кнопок, индикаторов и окон осмотра на общую палитру.
- **Не заменять 3D-арену статической панелью.** Строго сохранить скорость, управление, порядок ходов, цель, завершение боя, перезапуск и возврат.
- Визуальные эффекты и обновление WebGL-ресурсов требуют отдельного обоснования.

### UI-CONSOLIDATE-001 — очистка legacy-слоёв

- Только после принятых экранов удалить действительно неиспользуемые старые селекторы, а не сносить CSS массово.
- Свести дублирующиеся правила после регрессионной проверки, уточнить документацию и дизайн-токены.

## 3. Общие критерии каждого PR

- Один экран или тесно связанная группа экранов за один PR.
- До изменений — проверить актуальные `main`, `docs/PROJECT_STATUS.md`, GDD/TDD и `docs/UI_DESIGN_SYSTEM.md`.
- Не менять названия `id`, обработчики, сохранения и данные, если дизайн-задача этого не требует.
- Сначала реально проверяемые сценарии (клик, навигация, состояние/обновление, закрытие диалога), затем CSS.
- CI Node, WebGL, landscape; отдельный мобильный чек-лист и подтверждение владельца после разрешённого слияния.
- В PR обозначить, какие области были визуально проверены только автоматикой, а какие — на физическом устройстве.
- При неудачном художественном результате менять локальную ветку/PR; не ломать уже принятые `home` и `collection`.

## 4. Неизменяемые до отдельного решения границы

- Основная платформа — mobile landscape, безопасные зоны Safari, без горизонтального переполнения.
- Бой, экономика, аккаунт, получение наград и сохранения — правила из соответствующих источников; визуальная миграция их не меняет.
- Связь тегов героя с каноном — существующие данные, без выдуманных фракций.
- Принятие визуального направления **не означает разрешение слить каждый PR**.

## 5. Рекомендуемый первый технический шаг

**UI-HERO-001: досье героя, затем выбор отряда.** Эти экраны напрямую продолжают уже принятый ростер, поэтому их проще проверить на последовательность «Коллекция → досье → назад → отряд → бой». Два отдельных PR предпочтительнее одного большого, если проверка сохранений или управления затронута.
