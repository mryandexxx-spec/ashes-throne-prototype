# LC-008B — единый Web Locks writer для progress.v3

**Статус: [В РАЗРАБОТКЕ], кодовый PR для проверки; НЕ разрешение на новые награды.**
Основание: `HANDOFF_2026-11-17_AFTER_REWARD007A.md`, `REWARD_POLICY_RECEIPTS_007A.md`,
`PROJECT_STATUS.md`, GDD 3.0 и фактический `main` 115e21a.

## Реальные авторы кошелька

- `SaveCore.save` → `ProgressV3Core.persist` — единая точка всех обычных v3 сохранений из `game.js`.
- Кампания: оплата/возврат энергии, симуляция, итог боя и награды/звёзды/фарм; `CampaignCore` имеет отдельный ключ для доменного прогресса.
- `DailyCore.record/claim/claimAll`, `LoginCore.claim`: меняют `progress`, затем пишут через `persistProgress`.
- Экипировка и прокачка: `ProgressCore.equip/equipItem/promoteGear/upgradeMany`, `StarCore`, `SkillCore`; тестовое пополнение и регенерация энергии тоже пишут через `persistProgress`.
- `ProgressV3Core.stage` — **второй реальный автор** того же ключа: первоначальная миграция v2→v3 и расширение набора героев. Его нельзя забыть.
- `RewardPolicyCore.claim` — **не подключён к игре**. Будущий прямой автор v3; для browser claim требуется реальный `ProgressWriterCore.exclusive` и подтверждённое `authorize`.
- Профиль, отряд, лорная кампания, OPS, T/N и model-cache хранят свои **отдельные ключи**. Их не надо ошибочно переносить в кошелёк.

## Решение и границы гарантии

**Не выдаём localStorage за CAS.** Один `localStorage.setItem` атомарно записывает строку,
но последовательность `getItem → compare revision → setItem` не атомарна между вкладками.
Выбран **одно-вкладочный активный сеанс** вместо рискованной переделки синхронных
транзакций. Браузер до выполнения `game.js` запрашивает `navigator.locks.request`
с именем `ashes-throne.progress.v3.writer` и `ifAvailable:true`. Только владелец
блокировки запускает game.js, миграции и все игровые обработчики. Вторая вкладка
получает явное сообщение и может нажать «Повторить» после закрытия первой.
При отсутствии Web Locks **игра не запускает пишущую часть**, чтобы не делать
небезопасных обещаний о сохранении.

`ProgressV3Core.stage` и `persist` дополнительно проверяют владение сеансом;
`saveRevision` и readback остались вторичной проверкой устаревшего/повреждённого
сохранения. У будущих `RewardPolicy` claims обязательна та же блокировка;
асинхронные claims выполняются по очереди внутри вкладки, а обычные сохранения
отклоняются на время proof/claim. Не использовать произвольный фиктивный
`exclusive` для реальных выплат.

При `pagehide` блокировка освобождается, а возврат из bfcache вызывает
перезагрузку и повторную загрузку кошелька. Ошибки/отказы записи сохраняют прежние
механизмы fail-closed; неоднозначная запись не должна автоматически повторяться
как новая награда. Вход с повреждёнными данными не должен перезаписывать сохранение.

## Неразрешимые без сервера или изменения протокола риски

1. **Старые уже открытые вкладки предыдущей версии** не знают о Web Locks
   и могут писать параллельно с новой. Полной защиты в смешанной версии нет;
   владельцу следует закрыть старые вкладки и перезапустить игру после обновления.
2. Web Locks могут отсутствовать в старых iOS/Safari (<15.4), WebView и приватных
   контекстах; второй сеанс заблокирован до освобождения первого. Это осознанный
   компромисс: сохранность данных важнее многовкладочного геймплея.
3. При долгой заморозке вкладки или ошибке реализации Web Locks в конкретном
   WebKit возможен зависший lock и необходимость закрыть браузер; тайм-аутный
   «localStorage lease» не добавлен, потому что он не гарантирует эксклюзивность.
4. **Доменный сейв и кошелёк остаются разными ключами.** Этот этап не даёт
   распределённой транзакции между ними. Для будущих призов нужно подтверждённое
   доменное событие + стабильный receiptId + recoverable retry.
5. Клиентский localStorage можно вручную подделать, он не защищён от
   удаления/очистки браузером, и это не облачная синхронизация.
6. Слишком частые записи или отсутствие освобождения Web Lock на конкретном
   физическом iPhone должны быть проверены до выдачи реальных наград.

## Проверки

- `tests/progress-writer-008b.test.js`: два независимых контекста с общим
  lock и storage; повторное открытие; старые v2/v3; отказ записи и неясный
  итог; коррупция; отсутствие API; очередь будущих синтетических claims.
- `tests/progress-writer-008b-browser.cjs` и GitHub Actions: **две настоящие
  вкладки** Chromium / WebKit на одном origin, повтор после закрытия,
  чтение последнего баланса и отказ без API.
- Существующие Node и браузерные тесты проекта должны оставаться зелёными.
- Реальный физический iPhone Safari **не проверялся этим PR**. Минимальный
  ручной тест: сверить футер `v0.3.184 · WALLET008B`; в первой вкладке
  сохранить изменение; в другой увидеть блокировку; закрыть первую,
  повторить вход во второй; убедиться в прежнем прогрессе; проверить
  возврат из фона, бой, завершение/повтор, экипировку, daily/login.

**Не менялись:** награды, лимиты, энергозатраты, формулы, боевой движок,
основной игровой UI и утверждённые правила. Этот PR не предназначен
для слияния без отдельного одобрения владельца.
